## เริ่มจากตรงไหน

ส่วนที่คุยกับ risk-decision และประกอบ `TripPlan` (`risk_points`, `build_plan`) เขียนไว้แล้ว มีเทสต์ใน `tests/`
งานหลักคือแก้ `fetch_routes()` ให้คืนเส้นทางจริงในรูปแบบเดิม ทำตามลำดับนี้:

1. เรียก OSRM (ไม่ต้องใช้ key ลองแล้วว่ากรุงเทพ-เชียงใหม่ได้ 2 เส้น)
   `GET {OSRM_BASE_URL}/route/v1/driving/{lng},{lat};{lng},{lat};...?alternatives=3&overview=full&geometries=geojson&annotations=duration,distance`
   พิกัดใน URL เป็น `lng,lat` คั่นหลายจุดด้วย `;` และถ้ามีหมุดระหว่างทาง OSRM มักให้เส้นเดียว (ไม่เป็นไร ส่ง warning ตามข้อ 8)
2. `stop_minutes` ได้จาก `legs[].duration` (วินาที) สะสมกัน
3. `samples` ไล่ตาม `legs[].annotation.distance` / `duration` ทีละช่วง เก็บจุดทุกประมาณ 20 กม. พร้อมนาทีสะสม
4. ย่อ `geometry` ให้ไม่เกิน 500 จุด แล้วแปลง `[lng, lat]` เป็น `{lat, lng}`
5. `pytest` ต้องผ่าน และ `make smoke` ต้องผ่าน

public server ของ OSRM มีไว้ทดลอง ห้ามยิงถี่ ต้อง cache (ข้อ 10) และบันทึก fixture ไว้ใช้วันนำเสนอ (ข้อ 11)

## จุดที่คนส่วนใหญ่พลาด (อ่านก่อนเขียน)

1. **สลับ lat กับ lng** บั๊กอันดับหนึ่งของงานแผนที่ API routing ส่วนใหญ่ (รวม openrouteservice) ใช้ GeoJSON ที่เรียง `[lng, lat]` แต่ระบบเราใช้ `{lat, lng}` แปลงที่ขาเข้าและขาออกของ service นี้ที่เดียว เขียนเทสต์ด้วยพิกัดกรุงเทพ (13.75, 100.50) ถ้าเส้นไปโผล่ทะเลแปลว่าสลับ
2. **คิดว่า routing API ให้เส้นทางสำรองมาเองเสมอ** OSRM ให้ได้ในทริปไกลแต่ไม่เสมอไป (โดยเฉพาะเมื่อมีหมุดระหว่างทาง) ส่วน openrouteservice ให้ `alternative_routes` แค่ระยะไม่เกิน 100 กม. ถ้าเหลือเวลาค่อยสร้างทางเลือกเอง เช่น
   - ใช้ `avoid_polygons` วงรอบจุดที่ risk-decision บอกว่า HIGH (ข้อจำกัด: พื้นที่ไม่เกิน 200 ตร.กม. และกว้าง/สูงไม่เกิน 20 กม. ต่อ polygon ทำเป็นสี่เหลี่ยมเล็กๆ รอบจุด)
   - หรือบังคับผ่านจุดกลางที่อยู่ห่างจากพื้นที่เสี่ยง
3. **ส่งทุกจุดของเส้นทางไปประเมินความเสี่ยง** เส้นทางยาวมีเป็นพันจุด ส่งไป risk-decision แค่จุดตัวอย่างทุกประมาณ 20 กม. + ทุกหมุด พร้อมเวลาไปถึงของแต่ละจุด
4. **ส่ง geometry ดิบไปหน้าเว็บ** ย่อเส้นให้เหลือไม่เกิน 500 จุดก่อนส่ง (เช่น Douglas-Peucker) ไม่งั้นหน้าเว็บหน่วงและ response ใหญ่เกิน
5. **คิดเวลาไปถึงผิด** เวลาถึงหมุดที่ N = เวลาออก + เวลาเดินทางสะสมทุกช่วงก่อนหน้า ไม่ใช่เวลาของช่วงนั้นช่วงเดียว และเก็บเป็น UTC
6. **เลือกเส้นแนะนำเอง** risk-decision เป็นคนเลือก (`recommended_route_id`) และตัดสิน `recommendation` ส่งทุกเส้นไปในคำขอเดียวพร้อม `duration_min` ของแต่ละเส้น แล้วตั้ง `is_recommended: true` ให้เส้นที่มันเลือกเส้นเดียว
7. **คำตอบขาด field** คำตอบของ `routes/plan` ต้องมีทุก field ของ `TripPlan` ยกเว้น `trip_id`, `trip_no` รวม `summary_th` และ `waypoints` ที่มี `forecast` กับ `risk_level` ของเส้นที่แนะนำ
8. **หาเส้นสำรองไม่ได้แล้วตอบ error** ต้องส่งเส้นเดียวพร้อม warning `ALTERNATIVE_ROUTES_UNAVAILABLE`
9. **risk-decision ล่มแล้วทั้งคำขอล่ม** ยังต้องส่งเส้นทางกลับไป พร้อม warning `WEATHER_UNAVAILABLE` และห้ามเดาความเสี่ยงเป็น LOW
10. **เผาโควตา** cache ผลเส้นทางด้วย key จาก ต้นทาง/ปลายทาง/หมุด ที่ปัดทศนิยม 3 ตำแหน่ง
11. **ลืม DEMO_MODE** บันทึกคำตอบจริงของทริปตัวอย่างเก็บใน `fixtures/` แล้วอ่านจากไฟล์เมื่อ `DEMO_MODE=true`

## ถือว่าเสร็จเมื่อ

- กรุงเทพ ผ่าน นครสวรรค์ ไป เชียงใหม่ ได้เส้นทางจริงบนถนน และเวลาถึงแต่ละหมุดสมเหตุสมผล
- ทำให้ risk-decision ตอบ HIGH กลางทาง (แก้ fixture) แล้วได้เส้นทางสำรองที่เลี่ยงจุดนั้นจริง
- ปิดเน็ตแล้วเปิด `DEMO_MODE=true` ทริปตัวอย่างยังได้ผลเหมือนเดิม
