# RUNBOOK.md - ถ้าพังจริงจะทำยังไง

หลักคิด 3 ข้อ

1. **พังบางส่วนต้องไม่ลากทั้งระบบล่ม** ส่วนที่ยังใช้ได้ต้องใช้ได้ต่อ แล้วบอกผู้ใช้ตรงๆ ผ่าน `warnings` (CONTRACT หัวข้อ 3)
2. **`dev` ต้องรันได้ตลอดเวลา** อะไรเข้าไปแล้วพัง revert ก่อน ค่อยหาสาเหตุทีหลัง
3. **ทุกโมดูลมีทางถอยที่เล็กที่สุด** ถ้าทำเต็มไม่ทัน ยังมีของให้สาธิตได้ (หัวข้อ E)

---

## A. API ภายนอกล่มหรือโดนจำกัดโควตา

| อาการ | ทำอะไรทันที | กันไว้ล่วงหน้า |
|---|---|---|
| Open-Meteo ตอบช้า/ตอบ error | weather-disaster ตอบค่าจาก cache ล่าสุดพร้อม warning `WEATHER_UNAVAILABLE` ถ้าไม่มี cache ก็ส่ง warning อย่างเดียว | cache ทุกคำขอ (ปัดพิกัดทศนิยม 2 ตำแหน่ง ปัดเวลาเป็นรายชั่วโมง) |
| GDACS / USGS / Thaiwater / TMD ใช้ไม่ได้ | ตัดแหล่งนั้นออก ใช้แหล่งที่เหลือ ส่ง `HAZARD_FEED_UNAVAILABLE` | แต่ละแหล่งแยก try/except ของตัวเอง แหล่งหนึ่งพังห้ามลากแหล่งอื่น |
| Thaiwater / TMD ยังไม่อนุมัติ key | ปิดด้วย env (ไม่ใส่ key = ไม่เรียก) ระบบต้องทำงานได้โดยไม่มี 2 แหล่งนี้ | ออกแบบให้เป็นของเสริมตั้งแต่แรก |
| Routing API (Longdo / openrouteservice) ล่มหรือโควตาหมด | สลับไปอีกเจ้าด้วย env ถ้าล่มทั้งคู่ ตอบ `UPSTREAM_ERROR` พร้อมข้อความให้ลองใหม่ | cache ผลเส้นทางตามต้นทาง/ปลายทาง/หมุด |
| หาเส้นทางสำรองไม่ได้ | ส่งเส้นเดียวพร้อม `ALTERNATIVE_ROUTES_UNAVAILABLE` | ดูข้อจำกัดของ openrouteservice ใน README ของ routing-engine |

## B. LLM ใช้ไม่ได้ (assistant-agent)

| อาการ | ทำอะไร |
|---|---|
| ผู้ให้บริการหลักล่ม / 429 / โมเดลถูกถอด | สลับไปตัวสำรองอัตโนมัติ (`LLM_FALLBACK`) ถ้าล้มทั้งหมด ตอบข้อความสุภาพพร้อม `LLM_UNAVAILABLE` |
| LLM ใช้ไม่ได้เลยตอนสาธิต | คำสั่งหลัก 3 แบบต้องมีตัวแยกคำแบบกฎตายตัวรองรับ: "เลื่อน Trip NN ไปวันถัดไป", "เลื่อน Trip NN เป็นช่วงเช้า/บ่าย/เย็น", "Trip NN อากาศเป็นยังไง" สาธิตได้แม้ไม่มี LLM |
| ใช้ key กลางแล้วโควตาหมด | ตอน dev ห้ามใช้ key กลาง ทุกคนใช้ key ตัวเอง key กลางเปิดใช้เฉพาะวันนำเสนอ |

## C. Service ในระบบเราเองล่ม

| อาการ | ทำอะไร |
|---|---|
| container ล้มแล้วขึ้นเองไม่ได้ | `make logs` ดูตัวที่ล้ม หา request_id ของคำขอที่พังแล้วไล่ log ทีละ service |
| risk-decision ล่ม | routing-engine ยังส่งเส้นทางกลับไปได้ ระดับความเสี่ยงไม่ทราบ ใส่ `WEATHER_UNAVAILABLE` ห้ามใส่ LOW เอง |
| routing-engine ล่ม | หน้า My Trip แสดง error พร้อมปุ่มลองใหม่ หน้าอื่นต้องใช้ได้ตามปกติ |
| weather-disaster ล่ม | Overview / Safety Map แสดงแผนที่เปล่าพร้อมแถบแจ้งเตือน ไม่ใช่หน้าขาว |
| api-backend ล่ม | ทั้งเว็บใช้ไม่ได้ **จุดเดียวที่ห้ามล่ม** compose ตั้ง `restart: unless-stopped` ไว้แล้ว แต่ Docker restart ให้เฉพาะตอน process ตาย ถ้าค้างแต่ไม่ตาย (health ไม่ผ่าน) ต้อง `docker compose restart api-backend` เอง เจ้าของโมดูล 4 ต้องทำให้ process จบการทำงานเมื่อต่อฐานข้อมูลไม่ได้ |
| เครื่องใครรันทั้งระบบไม่ไหว (RAM ไม่พอ) | รันเฉพาะตัวที่ทำอยู่ + api-backend เช่น `docker compose up api-backend routing-engine` ตัวอื่นเป็น stub ก็พอ |

## D. รวมงานแล้วพัง (git)

| อาการ | ทำอะไร |
|---|---|
| merge เข้า `dev` แล้ว `make smoke` ไม่ผ่าน | กดปุ่ม Revert ในหน้า PR ที่ merge ไป (หรือ `git revert -m 1 <merge commit>`) แล้ว merge PR revert นั้น ค่อยแก้ใน branch เดิม ห้าม force push |
| conflict ที่ไฟล์ของคนอื่น / `docker-compose.yml` / `Makefile` / lockfile | หยุด `git merge --abort` แล้วทักเจ้าของไฟล์ อย่าเลือกข้างเอง |
| เผลอ commit ไฟล์ `.env` หรือ API key ขึ้นไปแล้ว | ยกเลิก key นั้นที่หน้าผู้ให้บริการทันที แล้วออกใหม่ การลบ commit อย่างเดียวไม่พอ key ถูกดูดไปแล้ว |
| schema ฐานข้อมูลเปลี่ยนแล้วของคนอื่นพัง | เจ้าของโมดูล 4 ประกาศในกลุ่มทุกครั้งที่เปลี่ยน ทุกคน `make reset` แล้ว `make up` ใหม่ |
| เจ้าของโปรเจกต์ไม่ว่างรีวิว | งานไม่ต้องหยุด ทำต่อใน branch ตัวเองได้เลย ต่อ stub ไปก่อน PR รอคิวได้ |
| เจ้าของโปรเจกต์เปิด PR เอง | GitHub ไม่ให้ approve PR ตัวเอง ตั้ง branch ruleset ให้เจ้าของโปรเจกต์ (admin) อยู่ในรายชื่อ bypass แบบ "pull requests only" ให้เพื่อนสักคนรีวิวเป็นคอมเมนต์ก่อน แล้วเจ้าของ merge ด้วยสิทธิ์ bypass |
| PR เปิดผิด base ไปที่ `main` | เปลี่ยน base เป็น `dev` ได้จากหน้า PR (ปุ่ม Edit ข้างชื่อ PR) ไม่ต้องปิดเปิดใหม่ |
| Discord ไม่แจ้งเตือน | ดูแท็บ Actions บน GitHub ส่วนใหญ่คือชื่อ branch ผิดรูปแบบ หรือชื่อ secret ไม่ตรง |

## E. ทำไม่ทัน: ทางถอยของแต่ละโมดูล

ตัดสินใจเรื่องนี้ให้เร็ว อย่ารอจนใกล้นำเสนอ ถ้าโมดูลไหนดูไม่ทัน เปลี่ยนเป็นเวอร์ชันถอยทันที

| โมดูล | เวอร์ชันเต็ม | เวอร์ชันถอยที่ยังสาธิตได้ |
|---|---|---|
| 1 Overview | แผนที่ทริป + รายละเอียด + อากาศ area | แผนที่ + การ์ดทริปถัดไปแบบข้อความ |
| 2 My Trip | ฟอร์ม + popup สรุป + หลายเส้นทาง + แท็บขวา | ฟอร์ม + เส้นทางเดียว + popup สรุป |
| 3 Safety Map + แชท | หมุดตามชนิดภัย + รายละเอียด + แชท | หมุดสีตามระดับ + แชทข้อความธรรมดา |
| 4 api-backend | ครบทุก endpoint + Postgres | **ห้ามถอย** ถ้าจำเป็นใช้ SQLite แทน Postgres ได้ |
| 5 routing-engine | หลายเส้นทาง + เลือกเส้นปลอดภัย | **ห้ามถอยต่ำกว่า** เส้นทางเดียวจริงจาก routing API + เวลาถึงแต่ละหมุด |
| 6 weather-disaster | ทุกแหล่ง | Open-Meteo อย่างเดียว + GDACS |
| 7 risk-decision | ครบทุก recommendation | ระดับความเสี่ยงตามเกณฑ์ + `NORMAL`/`REROUTE`/`AVOID` (ตัด `DELAY`) |
| 8 assistant-agent | ถามตอบ + สั่งแก้ทริป | ถามตอบ + คำสั่งแบบกฎตายตัว 3 แบบ (หัวข้อ B) |

**เส้นที่ต้องสาธิตได้เสมอ ห้ามตัด**: login > สร้างทริป > กด Plan > เห็นเส้นทางพร้อมความเสี่ยงบนแผนที่

## F. วันนำเสนอ

- คืนก่อนนำเสนอ: `make reset && make up && make smoke` บนเครื่องที่ใช้จริง ไม่ใช่เครื่องใครก็ได้
- เตรียม `DEMO_MODE=true` ไว้: เจ้าของโมดูล 5 และ 6 บันทึกคำตอบจริงของ API ภายนอกสำหรับทริปตัวอย่างเก็บเป็นไฟล์ JSON ในโฟลเดอร์ `fixtures/` ของ service ตัวเอง แล้วให้ `DEMO_MODE=true` อ่านจากไฟล์นั้นแทน เน็ตหลุดก็ยังสาธิตได้
- เตรียมทริปตัวอย่างที่ตั้งใจให้เจอฝนหนัก เพื่อโชว์ว่าระบบแนะนำเส้นทางอื่นได้จริง
- อัดวิดีโอสาธิตสำรองไว้ 1 ชุด ถ้าเครื่องพังหน้างานเปิดวิดีโอแทน
- key ทุกตัวในเครื่องที่ใช้สาธิตต้องทดสอบแล้วว่ายังใช้ได้ภายใน 24 ชั่วโมงก่อนนำเสนอ

## G. หาต้นเหตุเร็วๆ

1. `make health` ดูว่าตัวไหนไม่ตอบ
2. เปิด DevTools ของ browser ดู response header `X-Request-ID` ของคำขอที่พัง
3. `docker compose logs | grep <request_id>` ไล่ดูว่าหยุดที่ service ไหน
4. ยิง endpoint ของ service นั้นตรงๆ ที่พอร์ตบนเครื่อง (8001 ถึง 8005) เพื่อแยกว่าพังที่ตัวมันหรือพังที่ตัวที่มันเรียกต่อ
